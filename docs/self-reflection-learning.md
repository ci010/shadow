# Self-reflection：从记录经历到形成理解

本文记录 2026-11-17 用户与助手确认的学习方向，并作为实现、旧知识处置和后续效果复查的依据。它是设计与实验协议，不是当前功能全部已实现的声明，也不授予删除历史、修改 Project 规则或扩大源数据访问的权限。

## 目标

学习不仅要避免重复错误、积累操作方法，还应形成对项目对象、关系、设计选择及用户目标的可修正理解。

- **Wiki 主要回答 what / why**：是什么、有哪些对象、对象之间的关系、为什么如此，以及有依据但未确认的用户目标假设。
- **Skill 主要回答 how**：遇到什么问题，如何操作、分支判断、验证、停止或恢复。
- **日志与原始会话保存发生过什么**：承担证据和历史检索，而不是自动变成默认上下文或知识正文。
- **Project conventions / 权限 / 当前 Work**仍是各自独立的权威来源；学习产物不替代它们。

知识不必每条都立即改变行动。一个清楚的概念、对象关系或设计解释本身有价值。反过来，写入成功、文件数量增长、重复出现、测试通过数，都不能单独证明学到了有价值的东西。

## 来自 Anthropic dreaming 的借鉴与边界

阅读材料：

- [The components of agent memory（2026-11-06）](https://www.anthropic.com/research/components-of-agent-memory)
- [Dreams API](https://platform.claude.com/docs/en/managed-agents/dreams)
- [Dreaming with a dynamic workflow（2026-11-02）](https://platform.claude.com/cookbook/managed-agents-cma-dreaming-with-a-dynamic-workflow)

借鉴的是“回看证据、修正并重组知识、验证后续效果”，不是增加后台摘要的次数。原始记录、笔记、主题知识、少量预加载入口是不同层次；内容可以在层次间移动，而不只是逐级生成摘要。

公开 cookbook 将单会话分析和整库 organizer 分开，要求用当前理解陈述知识而非复述会话，并维护带用途说明的主题索引。其 organizer 不负责凭空重新分析事实；合并时保留必要事实与日期，冲突无法判断时显式保留。

Dreams API 生成独立输出 store；cookbook 夜间示例则原地更新。不要误称所有 dreaming 都有人工审批。我们的实验应优先采用可比较、可回退的候选知识版本，不能从外部示例推导删除或外传 Project 数据的许可。

论文中的下游任务结果表明：知识组织有时提升准确性并减少搜索成本，有时没有收益，甚至比原始文档更冗长。不同模型的表现也不同。不得把其实验数字当作 Shadow 的效果保证。该文不以推测用户动机为主要研究目标；本文明确增加这一有边界的抽象目标。

## 三类抽象

1. **经历 → 对象与关系**：识别概念、职责、边界及相互关系。
2. **选择与纠正 → 目标与解释假设**：寻找能解释多个具体选择的项目或交互目标，允许竞争解释和后续推翻。
3. **尝试与结果 → 方法**：提炼适用条件、步骤、失败分支、验证和恢复，进入 Skill。

不要把三者强制套成一个“教训”模板。精确条款、标识符、命令、版本边界有时比概括更重要；短不是唯一目标。

## Wiki 的内容契约

正文优先回答一个可辨识主题的 what / why。按主题组织，而非按来源会话、消息序号或执行日期不断追加。

推荐的信息层次（不是每页强制字段）：

- 对象、关系或当前有依据的理解。
- 适用范围、重要约束与例外。
- 为什么：明确理由、机制解释或标记为假设的目标解释。
- 来源、信息日期和重要未验证项。
- 指向相关主题及 how 型 Skill 的链接。

“用户提出 → 助手计划 → 工作者报告 → N 项测试 → 提交 → 尚未重启”的逐段历史通常留在日志。正文只保留影响理解的结论、边界或关键转折；通过简洁归因与来源链接保留证据标准，不在每段重复整套免责声明。

主题扩张时应拆分或重新归类：例如通用工作台 tab 的身份与位置约束，不应永久埋在 Workflow 专属页面里。整合、改名、退役和索引更新是知识维护，不是必须生成新页面的理由。

### Why 的三种证据状态

| 状态 | 含义 | 保存和使用方式 |
| --- | --- | --- |
| 明确理由 | 用户直接解释了自己的目标或取舍 | 保留原意、范围、来源；不要扩成普遍偏好 |
| 机制解释 | 对系统行为的因果或结构解释 | 标明证据与验证边界；报告不是独立复验 |
| 动机/目标假设 | 模型从选择与纠正中提出的解释 | 明确标为推测，记录替代解释、适用边界和推翻条件 |

允许保存未获用户确认的解释假设，不要求每次打断用户求证；也不把重复摘要当作独立证据。优先解释具体任务或产品目标，不进行人格诊断，不推断敏感个人属性。

一条有价值的假设应能回答：

- 它解释了哪些实际选择或纠正？
- 有什么其他合理解释？
- 哪些范围外不能用，什么证据会推翻它？
- 后续什么观察能支持、收窄或纠正它？

例如，多次要求不同 tab 共用放置框架，可以支持“在该工作台设计中，用户可能重视统一对象模型与可组合交互”的假设；不能跳到“用户在所有场景都偏好极简”。

假设用于理解、提问和提出方案，不是授权，不覆盖明确指令、权限或当前事实。若它将改变任务范围或成为重要取舍依据，应明确说出推测并按现有决策流程确认。未经证实的动机不应作为默认注入的行为命令。

## 输入单位与触发

### 原则

**读取分片不是学习单元。** 为资源限制分页读取是实现需要；每一片都发布为独立经历，会制造大量中间状态摘要。

目标学习单元是相对完整的问题阶段：提出、尝试、纠正、结果或明确未决边界。无需等待整个长期复用会话永久结束，也不能把工具调用数量当作阶段完整性的证据。

### 初始策略

- 调度保持低成本定期检查；不必通过拉长所有 timer 来降低碎片化学习。
- 已 completed 且执行已安静的会话可提前进入：必须有宿主记录的 `completedAt`，且不早于最后人类输入。历史 `completed: true` 没有新鲜度标记时仍走静默阈值，不回填完成时间。completed 不表示成功或用户验收。
- 未 completed 但持续沉寂、没有运行/等待中的执行，可以反思已发生的部分。首轮实验使用 **24 小时**作为沉寂阈值，这是可调整的工程参数，不是用户指定天数。
- inactive 不能推导用户满意、认可、放弃或情绪。
- 活跃执行、待决询问和未完成的后台工作，不应因一段时间没有用户消息就被当作结束。
- 同一会话之后继续使用时，处理新的证据并重新整合相关主题，不重复计数、不自动恢复被明确推翻的解释。

### 需要分开实现的两个层次

1. **来源就绪门禁**：阻止活跃会话不断产生反思批次，保留原始游标与重试证据。
2. **阶段级读取与整合**：在资源预算内保留跨分片候选和语义进度，阶段结束后综合。不能只增大消息上限或提高频率就宣称完成。

大历史需要明确的阶段范围、可恢复读取进度及最终整合。现有已固定范围的失败批次不能被悄悄重切、丢弃或标记已读；新策略必须说明这些批次如何等待、恢复或经授权结束。

## 知识整理与消费

独立整理的职责包括：合并重复主题、搬移错放知识、更新冲突与过时内容、修复链接、维护带“何时读”说明的索引。它不同于把日志加工成 Skill 的 Encapsulator，也不同于确定性的断链检查。

初期不强制引入向量检索或更多 Agent。先让目录、标题、用途说明和主题链接足够清楚，再测量检索瓶颈。

默认上下文应小且有用：

- 索引说明主题内容和适用问题，而不只是文件名。
- 日志必须区分发生时间与学习写入时间；今天入库不等于今天发生，也不等于与当前任务相关。
- 无相关性信号时，不把其他会话的当天日志视作相关知识。
- 未确认的目标假设按需读取；不自动提升成 policy、个人画像或永久执行规则。
- 原始证据仍可检索，知识不替代来源。

## 旧知识与白板实验

用户提出清空旧学习的可能性，要求先判断保留价值；这不是无条件删除全部 memory 的授权。

### 分组处置

- **可保留种子**：少量有明确来源的核心对象关系、稳定约束、关键风险区分和有条件的方法。
- **需要重写**：核心有价值但混杂过程、重复免责声明或主题错放的页面。
- **退出默认消费**：普通进度、陈旧部署状态、重复记录、没有新增理解的过程摘要。
- **不随自动学习清空**：用户直接维护的资料、Project conventions、权限配置、原始会话/工具证据、源代码文档、内建及手工维护的 Skills。

白板优先指新的“活跃知识集合”，不等于永久抹去证据。若获批准，先明确范围和回退方式，再执行归档/替换；仅在需要且明确授权时永久删除。

### 不能仅删除页面

学习 journal、pending batches、日志、Encapsulator 的按修订发现、关键词索引和 Skill discovery 共同决定后续消费。只删除 Wiki，旧输入可能再次生成同样内容，旧 artifact 也可能失配。

一次正确的白板切换应：

1. 固定截止点和实际生效版本，记录所保留的种子集合。
2. 保存独立可恢复的旧知识快照，并确保它不仍作为活跃知识被扫描/注入。
3. 对旧在途批次、旧材料是否再学习及下游已消费状态作明确处置，不伪造成功回执、不把未读范围冒充已审阅。
4. 不清除原始来源；若选择仅学习截止点之后的数据，显式记录这个实验边界。
5. 验证关键词、搜索、日志注入和 Skill discovery 的实际可见集合。

2026-11-17，用户明确选择“保留少量种子：精简有价值的 what/why 与 how，其余旧自动学习归档后退出活跃消费”（本会话 decision `b817d617-543b-412f-9eeb-9ca8d9cc7c23`）。这是所选目标，不代表归档已执行；不包含永久销毁原始数据。

需要使用受支持、经过验证的知识管理/学习恢复路径；不能直接编辑内部 journal 来掩盖问题。当前只有逐条知识删除和普通 Skill 编辑能力，不足以原子处理归档、旧 pending 与重新学习边界；执行前须补足或验证这些条件。

### 2026-11-17 有界清点的建议

本轮目录有 44 篇 Wiki（包含 3 篇身份页），另有日志和会话摘要；辅助审读覆盖 23 篇非身份 Wiki 和 10 个带学习来源的 Skill，父会话另行交叉阅读若干页面。未读项不能据标题判定无价值，也未逐篇验证其全部原始证据或当前实现。

建议的是**少量种子加可回退归档**，不是原样保留全部“准确”的页面。准确复述一个 UI 小需求，并不自动意味着它值得作为白板实验的核心知识。

优先保留/浓缩的内容候选：

- LayerFS / VFS / Skill 的对象职责与关键语义，移出历史实施过程。
- 多设备 presence 是活动信号而非审批权的区别。
- topic / focus 与 tab 内容身份 / 放置位置的概念区分；已在当前指南清楚覆盖的操作规则不再复制。
- 普通请求优化保持既有上下文表示，与另行选定 compact 恢复路径的区别。
- 凭据本地保护、历史迁移覆盖和服务端撤销是不同问题。

按需方法候选：启动与清理错误分别呈现；dirty-worktree 的可比基线与失败归因；跨设备 checkout / build / loaded runtime 的区分。它们应是精简、有来源、有失效条件的 how，而不是把旧测试数和提交经历整篇带入。

退出默认消费的优先候选：旧架构迁移过程、部署/测试/同步流水、仅记录一次任务范围且没有解释或方法的页面，以及与现行内建指南重复的长篇技能。完整名单和清空范围须在实际切换前确认；上述不是自动执行的删除清单。

## 实施与验收分层

| 层次 | 可验收结果 | 不能据此宣称 |
| --- | --- | --- |
| 可靠性 | 原始来源与版本可追溯，失败可恢复，不越权、不伪报已读 | 内容一定有价值 |
| 内容契约 | what/why 与 how 分工，允许可反驳的目标假设，避免会话流水账 | 模型一定按提示词执行 |
| 来源就绪 | 活跃会话不入选；完成/沉寂可入选；后续新消息不丢失 | 已实现完整阶段理解 |
| 整理与入口 | 主题清楚、链接可用、用途说明有帮助，重复/错放内容减少 | 已证明用户收益 |
| 实际收益 | 可定位的后续使用改善理解、减少重复纠正或查找成本 | 每次读取都代表帮助 |

每个改动应在交付说明中标明属于哪一层。禁止用 applied 数、事件数或页面数量充当综合质量分数。

## 第一阶段的实现边界

本轮实现内容契约、来源就绪门禁及默认消费入口，不把整个设计包装成已交付：

- Reflector / Encapsulator 指导加入 what/why/how 分工、带竞争解释的目标假设，以及“读取分片不是完整阶段”的边界。
- 来源门禁使用宿主完成标记或 24 小时静默；权限过滤独立不变，新来源和旧 pending 一视同仁。
- 关键词入口可读取有界的 authored description / 标题；无 Work / working-set 信号时不自动注入其他会话日志。
- 保留原有来源游标、重试语义、六轮预算和物理范围，未改为完整语义阶段综合。

尚未交付：跨分片语义进度与最终整合、独立语义 organizer、结构化复用收益归因，以及已选定的旧知识归档/种子切换。尤其归档还缺少统一学习 epoch、所有消费入口的可见性隔离和可恢复维护操作；不得先删文件再补状态。

另有未接入运行时的 [维护基础协议](learning-maintenance-foundation.md)：提供纯 manifest/epoch 契约、全物理段 cutoff 捕获、不可变证据快照与可恢复 prepare 收据。它不改变活跃集合或学习状态，所有 apply 均明确 unsupported；真实归档仍须完成统一栅栏、epoch 与各消费入口隔离。基础测试不代表真实归档已执行或收益已验证。

源码、单元测试和 Git 同步不能证明当前后端已加载，也不能证明模型实际产出的质量。部署后以真实会话及知识产物复查。

## 7–14 天复查协议

从**实际加载新实现并开始产生新知识**算起观察 7–14 天。若到预约日期尚未部署，报告不足的观察天数，不把源代码提交日期当作生效日期。初次复查只读，不自动清理、重试旧学习或续订计划。

### 固定问题

1. 新 Wiki 能否解释对象与关系，还是仍在复述实施经过？
2. why 中明确理由、机制解释、目标假设是否区分？是否有解释力，是否避免过宽人格推断？
3. 是否看到后续证据支持、收窄或推翻某条解释，而不只是继续追加？
4. Skill 是否包含可复用方法及验证边界，还是泛泛的“注意检查”？
5. 来源是否在完成/沉寂之后被处理？是否仍将连续分片作为独立进度发布？
6. 主题组织、用途索引和日志相关性是否让查找更容易？
7. 后续任务是否实际利用知识，少重复解释、少走证伪路径或更好预测用户目标？没有观察到就写 unknown。

### 评估方法

按来源抽取少量完整案例，包括有产物、no_change、失败/partial 和假设被纠正的对照。比较新旧内容时使用相同问题和原始证据；不把新增知识的主题差异误当算法改进。

可建立三组只读问答对照：原始记录搜索；旧知识加搜索；新知识加搜索。事先写好问题与事实/解释边界，比较准确性、过时内容、找到证据的成本和解释质量。小样本不能外推总体胜率。

动机假设评估不以“模型自己觉得合理”为准：看其是否准确解释已知选择，是否产生可验证预测，以及后续用户纠正是否使它收窄或失效。不给猜测的数量设配额，不把用户没有反驳算作证实。
