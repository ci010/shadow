# WeChat reply acceptance and recovery

- Only completed `response` events are sent. Intermediate commentary and tool events stay in Web.
- `sendmessage` succeeds only when HTTP succeeds and its JSON object contains at least one of `ret` / `errcode`, with every present code a bounded integer equal to zero. This means **API accepted**, not delivered to a device or read by the user.
- HTTP, business rejection, invalid JSON/schema and unknown transport outcomes throw `WeixinDeliveryError`. Its reason and optional numeric status/codes are safe to surface; server text, URLs, tokens and original causes are not retained. No automatic retry is performed, including unknown outcomes that might already have been accepted.
- Both normal replies and independent decision prompts require a stored account credential and a nonempty context token. The implementation does not assume a 24-hour token lifetime.
- `context-tokens.json` now stores `{ token, updatedAt }` per chat. Legacy string values remain usable, with unknown update time left absent until a new inbound token is observed.
- `undelivered.json` holds only per-chat count, last failure time and the count eligible for a recovery notice. It does not copy reply content; original results remain in session history. A failed multi-part reply counts once even if an earlier part was accepted. Unknown transport outcomes are conservatively included in this count.
- A nonempty, allowed, deduplicated inbound message from the linked user (when configured), carrying a changed context token, enables a notice. The next final text reply appends `此前有N条回复未送达，可在Web查看` rather than sending a separate message. Media-only replies and decision prompts leave the notice pending for a final text reply. No old reply is replayed.
- Decision failures contribute to the count but successful decisions do not clear a pending final-reply notice. Notice counts are acknowledged only after API acceptance. Per-chat send serialization prevents concurrent final replies from acknowledging the same snapshot twice; failures newer than that snapshot remain counted.

Limitations: API acceptance cannot prove actual device receipt. Recovery metadata is local to the bot storage repository; it is not a cross-process delivery ledger. A crash between remote acceptance and local acknowledgement can leave a notice pending. Persistence failures propagate and require storage repair rather than silently claiming delivery.

## Send diagnostics

After the updated backend is built and restarted (or the source-running backend is restarted), `[wechat] reply`, `[wechat] part` and `[wechat] sendmessage` lines record structured JSON diagnostics:

- Each final reply or decision gets a new random `replyId`, unrelated to user/chat/session IDs. A reply starts after entering its existing per-chat send queue; its elapsed time excludes queue wait. `start` is followed by `api_accepted` or `failed`, with elapsed milliseconds and the number of parts attempted. `api_accepted` does **not** mean device delivery.
- `part` preflight assigns a 1-based local part number to each image/text send. It reports account/context token presence and, only when a valid nonfuture context-token timestamp exists, `contextTokenAgeMs`. Legacy timestamps remain unknown (field omitted); no expiry assumption is introduced. Local file-read failures can occur before any part preflight.
- Each `sendmessage` HTTP invocation has an independent random `attemptId`, the same reply/part association, and start/end elapsed time. No retries or additional sends are added. This channel currently sends each image and then the final text; these numbers describe existing sends, not new text splitting.
- Response diagnostics report numeric HTTP status when available. `contentType` is a fixed allowlist (`application/json`, `text/plain`, `text/html`, `other`, `missing`), never a raw header or its parameters. Transport failures have no response metadata. HTTP rejections do not read the error body for diagnostics.
- Successful HTTP responses are consumed once, replacing the former `res.json()` with `res.text()` plus `JSON.parse` for the same validation. No clone, second body consumption, body preview or added network read is performed. This preserves the preexisting whole-body buffering behavior and does not introduce a response-size limit or timeout; those would be separate transport-policy changes.
- For `malformed_response`, `structure` distinguishes `unreadable`, `empty` (including whitespace), `non_json`, and JSON `null`/`array`/`object`/primitive types. Objects report only the presence/type/validity of the two protocol codes `ret` and `errcode`; only bounded safe integer code values are recorded. `malformed=missing_codes` or `invalid_code` narrows object-validation failures. Missing and invalid codes still fail exactly as before.

Diagnostics never contain message/media content, user IDs, token values or hashes, arbitrary response text/values/keys, URLs, raw headers, status text, credentials, or raw exception causes. Existing non-send channel logs are outside this diagnostic change. Start/end records can be incomplete if the process terminates or a request never settles. These logs can explain future validation failures but cannot retrospectively classify old `malformed_response status=200` entries or prove whether an already-accepted response reached WeChat. No actual WeChat messages are required for the synthetic diagnostic tests.
